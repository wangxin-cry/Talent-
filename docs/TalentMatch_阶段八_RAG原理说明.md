# TalentMatch 阶段八：RAG 知识增强原理说明

> 配套文档：《TalentMatch_项目设计方案_V1.md》《TalentMatch_数据库设计_V1.md》
> 实现范围：简历 / 职位 / 面试题向量化，人才库语义检索，面试题生成增强，失败降级。

---

## 1. 这一阶段解决什么问题

前七个阶段已经能完成：职位管理、简历解析、人岗匹配、流程看板、AI 面试题、数据与成本统计。但仍有两个明显短板：

1. **检索只能靠关键词**。候选人写“流式计算”“消息中间件”，职位要求写“Kafka”“Flink”，字面不重合就搜不到，人才库沉淀不下来。
2. **面试题缺少“同类经验”参照**。只根据当前这份简历出题，题目容易模板化，也看不到历史上类似岗位问过什么。

RAG（Retrieval-Augmented Generation，检索增强生成）解决的就是这两点：

- 先把简历、职位、历史面试题转成向量存起来；
- 需要时用自然语言去“按意思”找相似内容；
- 把找到的材料作为参考交给 LLM，让生成结果更具体、更贴近真实经历。

核心原则：**检索负责“找事实”，LLM 负责“组织表达”**。检索结果不参与算分、不参与状态判断，避免不可复现。

---

## 2. RAG 的基本原理

RAG 分两个阶段：

```
离线阶段（写）
  文本 → 切片 → Embedding 模型 → 向量 → 向量索引 + 元数据

在线阶段（读）
  用户问题 → Embedding 模型 → 查询向量
           → 向量索引召回 Top-K
           → 元数据过滤/聚合
           → 拼接参考材料
           → LLM 生成答案
```

### 2.1 为什么用向量

Embedding 模型把一段文本映射成固定维度（本项目 1024 维）的浮点数组。语义相近的文本，在向量空间里的方向也相近。

因此比较两段文本是否相似，不需要字面重合，只需要比较向量夹角：

```
similarity = cos(A, B) = (A · B) / (|A| × |B|)
```

实现上先把所有向量做 L2 归一化，使 `|A| = |B| = 1`，此时余弦相似度就等于内积 `A · B`，可以直接用 FAISS 的内积索引，少一次除法。

### 2.2 为什么不能只把整份简历丢给 LLM

- 简历可能上万字，超出上下文或成本过高；
- 一份简历里只有一两个项目和问题相关，整份送入会稀释重点；
- 检索可以只取最相关的 1~2 段，既省 token 又更精准。

所以需要**切片（chunk）**：把长文本拆成语义相对完整的小段，每段单独向量化。

## 3. 整体架构

```
┌──────────────────────────── 业务层 ────────────────────────────┐
│ 简历解析完成 │ 职位创建/编辑/发布 │ 面试题生成完成              │
└───────┬───────────────┬──────────────────┬─────────────────────┘
        │               │                  │
        ▼               ▼                  ▼
┌──────────────────────── RAG 服务层（app/services/rag.py）──────┐
│ 切片 chunk → 调 embedding → 同步 rag_chunk → 写向量索引        │
│ 语义检索 → 元数据过滤 → 按候选人聚合 → 返回片段                 │
│ 面试增强 → 检索相似简历 + 历史题 → 注入 Prompt                 │
└───────────────┬──────────────────────────────┬────────────────┘
                │                              │
                ▼                              ▼
┌──────────────────────────┐    ┌────────────────────────────────┐
│ 向量层 vector_store.py   │    │ 元数据层 rag_chunk（SQLite/PG）│
│ FAISS IndexIDMap2        │    │ 文本、来源、过滤字段            │
│ 未安装时 numpy 兜底      │    │ 主键 = FAISS 的 int64 id        │
└──────────────────────────┘    └────────────────────────────────┘
```

设计要点：**文本与向量分开存**。

- FAISS 只擅长存向量和算距离，不存文本、不支持 SQL 过滤；
- 关系库存切片正文和元数据，负责过滤、展示、审计；
- 两边用同一个 `rag_chunk.id` 关联，FAISS 的 id 就是数据库主键。

## 4. 数据模型

### 4.1 `rag_chunk` 表

| 字段 | 作用 |
|---|---|
| `id` | 自增主键，同时作为 FAISS 的 int64 id |
| `doc_type` | `resume` / `job` / `question`，三类集合隔离 |
| `source_id` | 简历=candidate_id，职位=job_id，面试题=application_id |
| `chunk_key` | 确定性切片键，唯一约束，保证重复索引不产生重复行 |
| `content` | 切片正文，参与向量化和片段展示 |
| `chunk_meta` | JSON：chunk_type、job_id、candidate_id、category 等 |
| `is_deleted` | 逻辑删除标记 |
| `company_id` | 公司隔离 |

`chunk_key` 示例：

```
resume-12-profile
resume-12-project-0
resume-12-work-1
resume-12-skills
job-3-profile
question-8-0
```

### 4.2 索引文件

```
data/faiss/
  resume.faiss     # 或 .npz（numpy 兜底）
  job.faiss
  question.faiss
```

三类内容分开建索引，而不是塞进一个集合：

- 检索时天然按类型隔离，不需要额外 `doc_type` 过滤；
- 某类索引损坏或重建，不影响另外两类；
- 文件更小，加载更快。

## 5. 切片策略

切片质量直接决定检索效果。原则：**一段只讲一件事，保留名称、技术栈、动作和结果**。

| 类型 | 粒度 | 上限 | 关键信息 |
|---|---|---|---|
| 简历画像 | 每人 1 段 | 1500 字 | 当前职位、公司、年限、城市、学历、技能、简历摘要 |
| 简历项目 | 每个项目 1 段 | 1500 字 | 项目名、角色、技术栈、项目描述 |
| 工作经历 | 每段经历 1 段 | 1500 字 | 公司、职位、职责描述 |
| 技能 | 每人 1 段 | 500 字 | 技能列表，用于“会什么”类查询 |
| 职位 | 每个职位 1 段 | 1800 字 | 标题、部门、地点、年限、学历、职责、要求、必备/加分技能 |
| 面试题 | 每题 1 段 | 800 字 | 题干、考察点、引用依据、追问 |

约束：

- 单份简历最多 10 段（画像 1 + 项目 4 + 工作 4 + 技能 1），避免长简历产生过多向量；
- 内容不足 20 字直接丢弃，避免“岗位：后端”这类无信息切片；
- 手机号、邮箱用正则替换为 `[手机号]`、`[邮箱]`，PII 不进入向量内容；
- 职位技能 id 会先经 `Skill` 表解析成标准名，再写入切片。

## 6. 向量化

### 6.1 模型与参数

| 项 | 值 |
|---|---|
| 模型 | `BAAI/bge-m3` |
| 维度 | 1024 |
| 接口 | SiliconFlow OpenAI 兼容 `/embeddings` |
| 批量 | 32 条/次 |
| 单条截断 | 2000 字 |
| 归一化 | 服务端 L2 归一化 |

选择 bge-m3 的原因：中文语义效果好、1024 维在效果与存储之间平衡、SiliconFlow 上调用成本极低。

### 6.2 调用与重试

- 使用 `httpx` 异步调用，失败按指数退避重试；
- 返回数量或维度不符直接报 `EmbeddingError`；
- 配置了 `EMBEDDING_PROVIDER=mock` 时使用确定性哈希向量，测试不联网。

Mock 策略：把文本拆成英文词、中文单字和双字组合，哈希到固定维度并累加，最后归一化。相同词越多，向量越相近，足以验证“语义召回”和排序逻辑。

### 6.3 成本计量

每次真实 embedding 调用都会写一条 `ai_call`：

```
feature = embedding
model   = BAAI/bge-m3
input_tokens = 接口返回的 prompt_tokens
output_tokens = 0
```

单价在 `app/core/pricing.py` 中维护，当前按 0 元计；供应商调价只需改这一处，不改历史台账。

## 7. FAISS 原理与实现

### 7.1 为什么选 FAISS

对比过 Milvus、pgvector、numpy 后选择 FAISS：

- 它是库，不是服务：不用 Docker、不开端口、不增加运维故障点；
- Windows / Linux 都能用，Python 3.11 有现成 wheel；
- 几万条向量用精确检索就是毫秒级，完全够当前规模；
- 索引文件落本地磁盘，迁移只需拷文件。

### 7.2 索引结构

```python
index = faiss.IndexIDMap2(faiss.IndexFlatIP(1024))
```

- `IndexFlatIP`：暴力内积检索，**精确**，不近似、不丢召回；
- `IndexIDMap2`：允许自定义 int64 id，这里直接用 `rag_chunk.id`；
- 向量已归一化，内积等于余弦相似度，分数范围约 `[-1, 1]`。

为什么暂时不用 HNSW：

- HNSW 是近似索引，需要调参，数据量小时收益不明显；
- 当前数据量（几千到几万）Flat 足够快；
- 以后超过十万级，只需把 `IndexFlatIP` 换成 `IndexHNSWFlat`，上层接口不变。

### 7.3 写入、删除与持久化

| 操作 | 实现 |
|---|---|
| 写入 | `remove_ids` 去重后 `add_with_ids` |
| 删除 | `remove_ids` |
| 持久化 | `faiss.write_index` 写临时文件，再 `os.replace` 原子替换 |
| 加载 | 启动或首次使用时 `faiss.read_index`，维度不符则重建空索引 |
| 并发 | 每类索引一把线程锁，FAISS 操作放到 `asyncio.to_thread` |

内存占用：1024 维 float32 约 4KB/条，1 万条约 40MB。

### 7.4 numpy 兜底

如果 `import faiss` 失败：

- `vector_store` 自动切到 `NumpyStore`；
- 向量存在内存字典，查询时拼成矩阵做一次矩阵乘法；
- 持久化为 `.npz`，重启后加载；
- 检索结果与 FAISS 数学上一致，只是数据量大时变慢。

这保证了“没装 faiss 也能跑通验收”，也是降级能力的一部分。

## 8. 索引生命周期

### 8.1 触发点

| 事件 | 索引内容 | 执行方式 |
|---|---|---|
| 简历解析成功并提交 | 该候选人的简历切片 | 解析后台任务内直接调用 |
| 职位创建 / 编辑 / 发布 / 审批 | 该职位切片 | FastAPI `BackgroundTasks`，独立会话 |
| 面试题生成完成 | 该应聘记录下的题目 | `BackgroundTasks`，独立会话 |
| 手动重建 | 指定范围 | `scripts/reindex_rag.py` |

索引失败只记日志，不影响业务提交：简历照样建档成功，职位照样发布，面试题照样返回。

### 8.2 幂等同步流程

`_sync_scope` 的核心步骤：

```
1. 查出该来源下已有的切片（按 chunk_key 建映射）
2. 逐段比较：
   - 内容完全相同 → 跳过，不调 embedding
   - 内容变化或新增 → 进入待向量化列表
3. 批量调用 embedding
4. 新切片插入 rag_chunk，flush 拿到自增 id
5. 变化/新增的 id 写入 FAISS（先删后加）
6. 旧切片：从 FAISS 删除，再从 rag_chunk 删除
7. 提交事务
```

因此重复触发不会让切片数翻倍，也不会重复计费。

### 8.3 重建

```bash
python scripts/reindex_rag.py --scope all --rebuild
```

`--rebuild` 会：

1. 清空三类 FAISS/numpy 索引文件；
2. 删除对应 `rag_chunk` 行；
3. 遍历现有候选人、职位、面试题重新切片和向量化。

以下情况必须重建：

- 更换 embedding 模型或维度；
- 从 numpy 切到 FAISS（或反过来）；
- 切片规则有大改；
- 索引文件损坏或与数据库不一致。

## 9. 语义检索流程（人才库）

入口：`POST /api/v1/rag/search/resumes`

```
query: "做过高并发订单系统"
```

执行步骤：

1. **查询向量化**：`query → bge-m3 → 1024 维向量`；
2. **向量召回**：在 `resume` 索引中取 `top_k × 4` 个切片，多取一些留给后续过滤；
3. **元数据过滤**：
   - 只保留本公司；
   - 排除指定候选人（面试出题时排除本人）；
   - 可选只保留某职位的投递者（关联 `application`）；
   - 丢弃低于阈值 `RAG_MIN_SCORE` 的切片；
4. **按候选人聚合**：
   - 同一候选人多个切片取最高分；
   - 保留最多 2 段命中片段；
5. **补全画像**：关联 `candidate` 表，补姓名、当前职位、公司、年限、城市、技能；
6. **排序截断**：按分数降序取 `top_k`。

返回示例：

```json
{
  "query": "做过高并发订单系统",
  "total": 2,
  "available": true,
  "items": [
    {
      "candidate_id": 12,
      "name": "张伟",
      "current_title": "后端工程师",
      "years_experience": 5,
      "score": 0.82,
      "snippets": ["项目：订单中心；技术栈：Kafka、Redis；描述：..."],
      "skills": ["Java", "Kafka", "Redis"]
    }
  ]
}
```

前端“人才库”页展示相似度、命中片段，并可一键加入招聘流程。

## 10. 面试题 RAG 增强

### 10.1 两路检索

生成面试题时检索两类材料：

1. **相似候选人简历**：用职位要求构造查询，排除当前候选人，取 Top 3；
2. **历史面试题**：同一索引中取 Top N，同职位优先，其次按相似度。

查询文本由以下内容拼成：

```
职位标题 + 必备技能 + 任职要求（截断）+ 候选人当前职位
```

### 10.2 Prompt 注入

参考材料以独立字段放进 user prompt：

```json
{
  "职位": "...",
  "候选人": {...},
  "匹配缺口": {...},
  "参考材料（仅作灵感，禁止照抄）": [
    {"类型": "resume", "标题": "相似候选人：李娜（后端工程师）", "片段": "..."},
    {"类型": "question", "标题": "历史面试题（项目深挖）", "片段": "..."}
  ]
}
```

System prompt 同时约束：

- 每题必须引用简历中的具体项目、公司、技能或明确缺口；
- 至少 5 题的 `reference` 以「项目：」「技能：」「经历：」「任职：」「缺口：」开头；
- 参考材料只作灵感，禁止照抄，禁止编造材料中没有的事实。

### 10.3 输出与标记

- `source`：
  - `llm_rag`：LLM 生成且实际用了参考材料；
  - `llm`：LLM 生成但未用 RAG；
  - `template`：LLM 不可用，模板兜底。
- `rag_used`：是否使用了知识库；
- `rag_sources`：本次实际参考的简历/历史题，含类型、标题、分数、片段。

前端面试准备页展示“知识库参考”面板，并可用开关控制本次是否增强。

### 10.4 缓存指纹

指纹由以下字段拼接后 SHA-256：

```
题目版本(iq-v2) + JD 版本 + 简历内容 hash
+ 缺失/命中必备技能 + 年限差 + RAG 开关
```

作用：

- 同样的职位 + 简历 + 开关，重复点击直接读缓存，不重复调用 LLM；
- RAG 开/关生成两套缓存，互不污染；
- JD 修改（jd_version 变化）或简历更新（content_hash 变化）自动失效；
- `force=true` 可手动绕过缓存。

## 11. 降级与开关

| 开关 | 作用 | 关闭后的行为 |
|---|---|---|
| `RAG_ENABLED` | 检索总开关 | 不检索，面试题按普通模式生成 |
| `RAG_INDEX_ENABLED` | 写入开关 | 不再新增索引，已有索引仍可查 |
| `VECTOR_BACKEND` | `faiss` / `numpy` / `auto` | faiss 不可用时自动 numpy |
| 请求参数 `use_rag` | 单次面试生成开关 | 本次不检索 |
| 请求参数 `force` | 绕过题目缓存 | 强制重新生成 |

失败矩阵：

| 故障 | 表现 | 主业务 |
|---|---|---|
| embedding 未配置 | 检索返回空，`rag_used=false` | 正常 |
| embedding 请求失败 | 索引跳过，检索返回空 | 正常 |
| faiss 未安装/损坏 | 自动 numpy 或空索引 | 正常 |
| 索引写入异常 | 记日志，不回滚业务 | 正常 |
| LLM 不可用 | 模板题兜底 | 正常 |

设计底线：**RAG 永远是可选的增强，不是主链路的依赖**。

## 12. 成本与性能

| 项 | 数量级 |
|---|---|
| 单条 1024 维向量 | 约 4KB |
| 1 万条切片 | 约 40MB 内存 + 40MB 磁盘 |
| Flat 检索 1 万条 | 毫秒级 |
| embedding 批量 | 32 条/次 |
| 面试增强额外 token | 约 5 条参考材料，每条 ≤260 字 |

省钱手段：

- 内容未变化不重复 embedding；
- 面试题指纹缓存；
- RAG 开关可按需关闭；
- 只给 Top-N 结果生成理由/题目，不做全量 LLM 处理。

## 13. 局限与生产化建议

当前实现刻意保持简单，已知限制：

1. **单进程索引**：FAISS 在进程内，后端需单 worker；多实例部署应换 Milvus/pgvector 或做索引服务化。
2. **过滤在应用层**：FAISS 不支持 SQL 过滤，先多召回再在 Python 里筛；数据量很大时效率下降。
3. **Flat 全量扫描**：十万级以上建议换 HNSW/IVF。
4. **索引与数据库有短暂窗口**：先写库再写向量，极端情况下可能短暂不一致；重建脚本可修复。
5. **模型/维度变更必须重建**：旧向量与新查询不在同一空间，不能混用。
6. **PII 处理**：切片阶段已脱敏手机号和邮箱，但简历正文仍可能包含其他敏感信息，生产环境应加访问审计。

## 14. 测试与验收

| 验收项 | 测试方式 | 结果 |
|---|---|---|
| 语义搜相似简历 | 构造 Kafka/风控与 Vue/前端两份简历，查询“Kafka 实时风控” | 正确召回后端候选人，分数更高 |
| 索引幂等 | 连续索引同一候选人两次 | 切片数不增长 |
| 持久化 | 清空内存注册表后重新检索 | 仍能召回 |
| 排除本人 | `exclude_candidate_id` | 结果不含本人 |
| 开/关 RAG 生成 | 模板、LLM、LLM+RAG 三条路径 | 均输出 6~8 题 |
| 参考来源 | 检查 `rag_sources` 与 Prompt | 含简历/历史题，Prompt 出现“参考材料” |
| 缓存隔离 | RAG 开/关分别二次调用 | 各自命中缓存 |
| 向量化失败 | 模拟 `EmbeddingError` | 索引返回 0、搜索为空、面试题正常 |

## 16. 三分钟答辩讲法

1. **问题**：关键词检索搜不到“意思相同、字面不同”的简历；面试题缺少同类经验参照。
2. **方案**：把简历/职位/历史题切片，用 bge-m3 转成 1024 维向量，FAISS 建索引；查询时先向量召回，再按公司和候选人过滤聚合。
3. **增强**：面试题生成前检索相似候选人和历史题，作为“仅作灵感”的材料注入 Prompt，并要求每题引用具体项目或缺口。
4. **可靠性**：文本与向量分离、切片幂等、指纹缓存；embedding/FAISS 任一失败都自动降级，主流程不受影响。
5. **验证**：语义召回、幂等、持久化、开关隔离、失败降级均有测试；开关两种模式都能稳定生成 6~8 题。
6. **取舍**：当前规模用 Flat 精确检索，十万级再换 HNSW；单进程 FAISS 适合当前部署，多实例时再换服务化向量库。
