## 四、发现并修复的 4 个问题

### ① 追问状态下换意图，新请求被吞（P1，体验缺陷）

| 项 | 内容 |
|---|---|
| 现象 | 追问「要发布哪个职位？」时，用户改说「给候选人排个序」→ 系统回一句能力清单，intent=None |
| 根因 | `pending_failed` 一刀切：只要上一轮追问没补上，新请求即使识别出来也被置为 None |
| 影响 | 用户会觉得"说了半天没反应"；多轮对话体验断裂 |
| 修复 | 只在**同一意图**追问连续失败时才退回能力清单；换意图照常执行（并给出新追问） |
| 效果 | 修复后：「给候选人排个序」→ intent=match + 新追问「用哪个职位来做这次操作？」 |
| 测试 | `test_switching_intent_during_clarification_is_respected` |

### ② 会话列表 N+1 查询（P2，性能）

| 项 | 内容 |
|---|---|
| 现象 | `session_payload` 每个会话各查一次 COUNT + 一次最后消息：50 个会话 = **100 次查询** |
| 修复 | 新增 `session_payloads()` 批量组装：两条聚合查询搞定 |
| 效果 | 5 个会话的列表请求 3 次共 **37ms**（约 12ms/次） |

### ③ 空会话堆在侧栏（P3，体验）

| 项 | 内容 |
|---|---|
| 现象 | 点「新会话」但没说话，该会话一直出现在列表里（0 条消息） |
| 修复 | 列表默认过滤 `message_count=0`；保留 `include_empty=true` 参数供调试/恢复 |
| 测试 | `test_empty_session_hidden_by_default`（默认隐藏 / 显式包含 / 发消息后入列） |

### ④ 意图规则词序固定，漏识别（P3，准确率）

| 项 | 内容 |
|---|---|
| 现象 | 「把职位上架」识别不出发布意图（规则写死「上架职位」）；「给候选人排个序」识别不出匹配 |
| 修复 | 发布规则支持词序变化（`发布.{0,6}职位|上架.{0,6}职位|职位.{0,6}上架|...`）；补「排个序」「有哪些…候选人」等口语变体 |
| 效果 | 路由准确率 20/20（原有测试集），29 条扩展压测 28/29（唯一"误判"是期望写错：淘汰本就属于 `reject_candidate`） |
| 测试 | `test_word_order_variants_route_correctly`，并把 20 条门槛从 ≥16 提到 **≥19** |

## 六、设计上值得肯定的点

1. **规则优先、LLM 兜底**：高频意图零成本、零延迟；LLM 只处理规则不覆盖的说法，且失败不阻塞
2. **追问不重复**：`pending` 机制把待补槽位挂在消息卡上，同一意图只问一次
3. **安全闸落到数据**：确认卡 `card_data.status=pending`，`confirm_action` 校验状态，避免重复确认
4. **卡片结构化**：`card_data` 存 JSON 而非 HTML，前端可重渲染、可换 UI（设计文档要求）
5. **状态机不被绕过**：确认后仍走 `pipeline.change_status`，非法迁移如实拒绝并标记降级
6. **错误可展示**：「候选人不存在：999999」「用哪个职位来做这次操作？」都是人话
