# TalentMatch 对话式交互与产品画面设计（V1）

> 配套文档：《TalentMatch_项目设计方案_V1.md》（架构与分阶段计划）
> 本文回答三个问题：**① 我能不能直接打字？② Manager Agent 怎么听懂并干活？③ 做出来界面上是什么样？**

---

## 0. 先直接回答你的问题

**问：我直接输入内容就行吗？**

**答：可以，而且这就是本产品的核心交互。** 设计成"像跟 AI 助手对话"一样：你打一句话，Manager Agent 自己判断你要干什么、该调哪个能力、需要哪些参数，然后执行并给你结果——和你现在跟我对话的原理完全一样。

**对比一下就更清楚**：

| | 你和我（AI 助手） | 你和一个业务系统（TalentMatch） |
|---|---|---|
| 你说话 | "帮我看看这个文件有没有问题" | "看看这批简历谁适合后端岗" |
| 它理解 | 意图 = 检查文件；参数 = 文件 | 意图 = 匹配；参数 = 批次 + 职位 |
| 它调用 | 读文件工具、搜索工具 | 解析简历、匹配引擎、生成面试题 |
| 它回答 | 一段分析 + 建议 | 排名表卡片 + 理由 + 下一步选项 |

**但有一句必须说在前面**：纯聊天机器人做招聘系统是**不够的**。有两类操作不适合"说一句话就执行"：

- **批量、精确的编辑**（改 20 个职位的状态）→ 表格 + 批处理更可靠；
- **不可逆、有后果的操作**（淘汰候选人、发布职位）→ 必须有确认和明确按钮。

所以最终产品是 **双形态**：对话是"主入口和自然语言外壳"，专业页面是"精确操作和可视化"。**同一套后端能力，两个入口。**

## 1. 两种交互形态的分工

| 形态 | 适合什么 | 典型例子 | 在本项目中的定位 |
|---|---|---|---|
| **对话式（Chat）** | 意图模糊、需要组合多个能力、需要解释和追问 | "这批人谁最适合后端岗，给前三个出面试题" | **主入口**，80% 的日常操作 |
| **页面式（Form / Dashboard）** | 批量、审批、精确字段编辑、图表看板 | 职位列表批量下架、候选人信息精修、漏斗图 | **专业操作区**，复杂和可视化场景 |

**统一原则**：
1. 对话里能发起的能力，页面上也一定有个按钮（保证不依赖 AI 也能干活，AI 挂了系统还能用）。
2. 页面上做的事，对话框里也能查到（"张伟现在什么状态？"）。
3. 两边操作同一套后端接口，不做两套逻辑。

### 1.1 关键澄清：页面式 ≠ 绕过子 Agent

很多人会以为"页面式就是不走 AI、直接查数据库"。**不对。** 准确的说法是：

> **两种入口的区别只在于"意图是怎么来的"：**
> - **页面式 = 显式调用**：用户点了哪个按钮、填了哪个表单，意图和参数已经由 UI 明确表达了 → **跳过意图识别**，直接调对应的能力（子 Agent 或普通 service）。
> - **对话式 = 意图推导**：用户打一句话，意图和参数都不明确 → 需要 Manager 识别、抽取、规划，再调能力。

两条路殊途同归，最后都落到**同一套能力层**：

```
页面式                                      对话式
[人才库页] 选技能Go+年限5年 → [查询]        "找找会Go的、5年以上的，看看适不适合后端岗"
      │                                              │
      │ 意图已明确，参数已知                          │ Manager: 识别意图 + 抽参数 + 规划
      │ （跳过意图识别）                              │
      └──────────────┬───────────────────────────────┘
                     ▼
            ┌────────────────────┐
            │  同一套能力层       │
            │  search_candidates │  ← 检索（确定性服务）
            │  MatchEngineAgent  │  ← 匹配（规则打分+LLM理由）
            │  InterviewAgent    │  ← 面试题
            └────────────────────┘
```

**所以回答你的问题**：对"对历史简历做人才筛选"这种操作，页面上点按钮就是**直接调用对应能力**（可能是匹配子 Agent，也可能只是个查询），不需要 Manager 再去猜你要干什么——因为按钮上已经写着"人才库筛选"了。

### 1.2 页面操作背后到底是什么（用不用 Agent）

> 关键判断：**不是所有页面操作都要 Agent**。能力明确、参数结构化的，直接走确定性服务更快更稳。

| 页面操作 | 背后是什么 | 用 Agent 吗 | 原因 |
|---|---|:--:|---|
| 人才库按条件筛（技能/年限/学历/城市） | 结构化查询（SQL / JSON 过滤） | ❌ 不用 | 条件明确，无需理解 |
| 人才库语义搜（"做过分布式交易系统的"） | RAG 向量检索 | ❌ 不用生成型 Agent | 检索即可，不需要生成 |
| 拿一个职位匹配人才库/应聘者 | `MatchEngineAgent` | ✅ 用 | 需要写匹配理由（LLM） |
| 生成面试题 | `InterviewAssistantAgent` | ✅ 用 | 需要生成 |
| 推进候选人状态 | `WorkflowAutoAgent`（校验用状态机） | ✅ 弱用 | 校验不用 LLM，通知措辞可润色 |
| 看板数字 | 统计查询 | ❌ 不用 | 纯计算 |
| 看板洞察文案 | `AnalyticsAgent` | ✅ 用 | 需要讲人话 |

**一句话**：页面式 = "我已经知道要调什么，直接调"；对话式 = "我不确定该调什么，你帮我判断"。

### 1.3 用例：对历史简历做人才筛选

这是你举的场景，拆成两种做法：

**做法 A：人才库检索（页面式，最快）**

```
人才库页
├─ 筛选条件：技能 [Go, K8s] · 年限 ≥5 · 学历 本科+ · 城市 上海
├─ 关键词："微服务"（走语义检索）
└─ [查询]
     → 后端：search_candidates(filters, keyword)
     → 返回：候选人表格（姓名/年限/技能/最近公司/入库时间）
```

背后**不需要 Agent**：结构化条件走 SQL/JSON 过滤，关键词走 RAG 检索。秒出。

**做法 B：拿职位去匹配人才库（页面式 + Agent）**

```
职位详情页（Python 后端工程师）
└─ [从人才库匹配]  ← 按钮
     → 选择范围：○ 只匹配投递本职位的人  ● 匹配全人才库
     → 后端：MatchEngineAgent(job, scope=talent_pool)
     → 返回：排名表卡片（分数/命中/缺失/理由）
```

这里**要 Agent**：因为需要算分 + 写可解释理由。

**做法 C：对话式（把 A 和 B 串起来）**

```
👤 从人才库里找找会 Go 的、5 年以上的，看看适不适合这个后端岗
🤖 意图 = search_candidates + match_job
   槽位：skills=[Go]、min_years=5、job=当前职位（上下文推断）
🤖 先检索出 6 人 → 再用当前职位匹配打分
   [结果卡] 6 人排名，最高分 81
```

对话式的价值不在"能做 A 或 B"，而在**能把它们组合起来并解释**。

### 1.4 由此得出两条设计规则

1. **能力注册表是唯一真相**：每个能力（检索/匹配/面试题/状态）只实现一次，同时暴露为「页面按钮」和「对话工具」。页面加了新功能，对话自动也能用；反之亦然。
2. **能确定性算的就不进 Agent**：页面式很多操作连 Agent 都不需要——这既快又便宜。**Agent 只用在需要理解/生成的地方**（这与主设计文档 §5.3 的边界原则一致）。

## 2. Manager Agent 怎么"听懂"你的话

一句话进来，内部走五步：

```
① 意图识别     这句话要干什么？（可能不止一个意图）
      │
      ▼
② 槽位抽取     需要哪些参数？话里有没有？没有就去上下文找 / 追问
      │
      ▼
③ 任务规划     拆成哪几个子任务、按什么顺序（DAG）
      │
      ▼
④ 执行调用     调子 Agent / 工具（带当前用户身份鉴权）
      │
      ▼
⑤ 结果呈现     结构化卡片 + 一句自然语言总结 + 下一步选项
```

### 用一个真实例子走一遍

**你说**：「帮我把刚传的这批人里最合适的三个挑出来，然后给他们出面试题」

**内部发生的事**：

| 步骤 | 做了什么 | 结果 |
|---|---|---|
| ① 意图识别 | 识别出**复合意图**：`match_job` + `generate_interview` | 两个意图，有先后依赖 |
| ② 槽位抽取 | `job` = 话里没提 → 从**上下文**取"当前职位 = Python 后端工程师"；`candidates` = 从上下文取"最近批次 9 人"；`top_n` = 3 | 参数齐了，不需要追问 |
| ③ 任务规划 | 建 DAG：`MatchEngine(9人)` → 取 top3 → `InterviewAssistant × 3`（并行） | 顺序确定 |
| ④ 执行 | 先调匹配（规则打分 + 写理由），把匹配出的"缺口"通过上下文总线传给面试 Agent | 匹配结果 → 面试题 |
| ⑤ 呈现 | 一张排名卡 + 三张面试题卡 + 总结句 + 成本 | "已为张伟、李娜、王强生成面试题，耗时 12s，花费 ¥0.08" |

**注意三件事**：
- **参数缺失不用你重说**：它先去上下文找（当前职位、最近批次）；实在找不到才追问「是哪个职位？」——这就像你跟我说"改一下那个文件"，我知道你说的是刚才那个。
- **复合意图会自动排顺序**：出面试题需要先知道匹配缺口，所以匹配一定在面试前面。
- **每个动作带你的身份**：调工具时用的是当前登录用户的权限，AI 不能绕过权限。

### 为什么它能听懂

原理就是 **LLM 的 function calling（工具调用）**：
1. 把"可用工具清单 + 每个工具的说明和参数格式"告诉 LLM；
2. LLM 判断该调哪个工具、参数填什么，输出结构化调用请求；
3. 系统执行工具，把结果回给 LLM；
4. LLM 决定是继续调下一个工具、还是给最终答复。

你跟我对话时，我的"工具"是读文件、搜索、跑命令；TalentMatch 的"工具"是解析简历、匹配、生成面试题、推进状态。

## 3. 它能调用哪些工具（对话的能力边界）

> 这张表定义了"对话能干什么"和"哪些必须确认"——是安全设计的核心。

| 工具 | 对应能力 | 危险等级 | 默认行为 |
|---|---|---|---|
| `parse_resume` | 解析上传的简历入库 | 写（低风险） | 上传后自动执行 |
| `search_candidates` | 人才库语义检索 | 读 | 直接执行 |
| `match_job` | 职位 × 候选人匹配排名 | 读（算） | 直接执行 |
| `generate_interview` | 生成面试题 | 读（生成） | 直接执行 |
| `generate_jd` | 生成/优化 JD 草稿 | 读（生成草稿） | 直接执行 |
| `query_analytics` | 查漏斗/周期/渠道数据 | 读 | 直接执行 |
| `get_application_status` | 查候选人进度 | 读 | 直接执行 |
| `publish_job` | 发布职位 | **写** | **先出计划，确认后执行** |
| `advance_status` | 推进候选人状态 | **写·不可逆** | **必须确认 + 校验迁移合法** |
| `reject_candidate` | 淘汰候选人 | **写·不可逆** | **必须确认 + 必填原因** |
| `export_report` | 导出报表 | 读（含 PII） | 直接执行但留审计 |

**三级安全策略**：

| 级别 | 策略 | 例子 |
|:--:|---|---|
| 🟢 读/生成 | 直接执行，无需确认，结果可重来 | 匹配、面试题、查数据 |
| 🟡 受控写 | **先出"执行计划"让用户确认**，可修改再执行 | 发布职位（先展示要发布的内容） |
| 🔴 不可逆写 | **强制二次确认 + 展示影响面 + 必填原因** | 淘汰、批量状态变更 |

### 4.2 三个区域各自的职责

| 区域 | 作用 | 关键点 |
|---|---|---|
| **左栏·会话列表** | 按主题管理多轮对话 | 每个招聘任务一个会话（如"Python 岗筛选"），可切换回看 |
| **中间·对话区** | 你说话、AI 回话、卡片呈现结果 | 消息流 + 内嵌交互卡片（上传区/表格/按钮） |
| **右栏·上下文面板** | 显示"AI 现在脑子里在想什么业务对象" | 当前职位、最近批次、今日数据；**随时可切换当前位置**，切换后对话跟着变 |

**这个右栏是关键设计**：没有它，用户不知道 AI 在拿哪个职位做匹配，容易张冠李戴。有了它，"当前职位"一目了然，且可以点掉换一个。

### 4.4 一次完整会话的分镜（屏幕上依次发生什么）

> 这是你问的"做出来的画面"——按顺序描述用户看到的东西。

**第 1 步：进入工作台**
打开页面 → 左边是最近的会话，中间是对话区，右边显示"当前职位：Python 后端工程师（招聘中）"，底部是输入框。

**第 2 步：上传简历**
你说「我传了一批简历」。对话里立刻出现**上传卡**（不是弹窗），你拖进 10 个文件。卡片变灰提示"正在上传 10 份…"。

**第 3 步：自动解析**
上传完，AI 自动回复「收到 10 份，开始解析」，并显示**进度条**（6/10）。你不用做任何操作——这就是"先解析"。

**第 4 步：出解析结果**
进度条走完，出现**解析结果卡**：9 份成功列出姓名/年限/技能，1 份标红"扫描件无法识别"并带[重试][手动录入]按钮。右侧面板"最近批次"更新为"10 份 · 9 成功 1 失败"。

**第 5 步：你下指令**
AI 问「要看看这些人适合哪些在招职位吗？」并给出三个职位按钮。你点「Python 后端工程师」，或直接打字「看看谁适合后端岗」。

**第 6 步：匹配**
AI 回「正在对这 9 人做匹配…」，几秒后出现**排名卡**：第 1 名张伟 87 分，命中/缺失技能一目了然，带"展开完整理由"。你说「前三个展开看看」，它就把前三名的理由都展开。

**第 7 步：生成面试题**
你说「给前三个都出面试题」。AI 回「好，正在为张伟、李娜、王强生成…」，然后连出**三张面试题卡**。总结句：「已生成 24 道题（每人 8 道），耗时 12s，花费 ¥0.08」。

**第 8 步：推进状态**
你说「把张伟推到面试」。AI 弹出**状态流转确认卡**：「新申请 → 面试中，会跳过筛选中并触发面试邀请通知，确认吗？」你点[确认推进]。卡片变成"✓ 已推进"，对话里补一句「已更新状态并发出面试邀请」。

**第 9 步：看数据**
你问「这个月各渠道怎么样？」。AI 调分析工具，出**图表卡** + 一句洞察。

**第 10 步：随时回看**
左栏这个会话叫"Python 岗筛选"，下次点开还在；右栏可以换职位，换完再说"这批人适合吗"就按新职位算。

## 6. 关键难点与设计解法

> 这节是"看起来简单、做起来会翻车"的地方，提前设计好就不用返工。

| # | 难点 | 翻车表现 | 设计解法 |
|:--:|---|---|---|
| 1 | **意图误判** | 说"看看简历"，它去发布了职位 | 意图置信度低于阈值 → **给选项**而不是瞎执行；高频意图走规则兜底 |
| 2 | **参数缺失** | 说"匹配一下"，它问"哪个职位"问到烦 | 先查上下文（当前职位/最近批次）→ 找不到才追问，且一次只问一个 |
| 3 | **幻觉调用** | 它编了个不存在的候选人 id | 工具参数**必须过白名单 + 存在性校验**；查不到就明说"没找到" |
| 4 | **不可逆误操作** | 一句话把 20 人淘汰了 | 三级安全策略（§3）：写操作先出计划、不可逆强制确认 |
| 5 | **结果纯文本难用** | 排名用一段话列，没法点开 | 结果**卡片化**（表格/按钮/展开），不是纯 Markdown 文字 |
| 6 | **多轮上下文丢失** | 第二轮它忘了刚才那个职位 | 会话记忆：最近 20 轮 + 业务上下文（当前职位/候选人/批次） |
| 7 | **每句话都调 LLM 太贵** | 每分钟都在烧 token | 规则优先（关键词/快捷按钮）→ 规则不命中才上 LLM；意图结果缓存 |
| 8 | **权限被绕过** | AI 说"可以删"就真删了 | 工具调用**带当前用户身份**，RBAC 在工具层校验，AI 无权越级 |
| 9 | **无法回退** | 点错确认，状态错了 | 写操作留审计 + 提供反向操作入口（如"撤回淘汰"走特殊接口） |
| 10 | **AI 挂了系统不能用** | 全站瘫痪 | 对话只是"壳"，页面按钮走同一套接口；AI 挂了还能用页面 |

## 7. 这部分落在十阶段计划的哪里

| 阶段 | 做什么 | 与本设计的关系 |
|:--:|---|---|
| 三 | 职位管理 + `JDWriterAgent` | 提供 `generate_jd` 工具 |
| 四 | 简历解析 | 提供 `parse_resume` 工具，**上传卡**就是这里做的 |
| 五 | 匹配 | 提供 `match_job` 工具 + **排名卡** |
| 六 | 流程 + 面试题 | 提供 `advance_status` / `generate_interview` + **题卡/确认卡** |
| 七 | 看板 + 成本 | 提供 `query_analytics` + **图表卡** |
| 九 | **多 Agent 编排** | Supervisor 有了，**但还缺"对话入口"** |
| **九½（新增）** | **对话式网关（Chat Gateway）** | 意图识别 + 槽位抽取 + 计划确认 + 卡片渲染，把上面所有工具暴露成"会说话的能力" |

**新增阶段九½ 的具体内容**（约 4~5 人日）：

1. **工具注册表**：把阶段三~七的能力统一封装成"带说明+参数 schema"的工具，注册给 LLM。
2. **Manager 的对话版**：意图识别 → 槽位抽取（含上下文推断）→ 缺参追问 → 规划 → 调 Supervisor。
3. **三级安全闸**：读直接执行 / 写先出计划 / 不可逆强制确认。
4. **会话记忆**：最近 20 轮 + 业务上下文（当前职位/候选人/批次）。
5. **卡片渲染**：上传卡、解析结果卡、排名卡、面试题卡、确认卡、图表卡。
6. **前端对话页**：三栏布局（会话列表 / 对话流 / 上下文面板）+ 卡片组件。

**最小可用版本（先做）**：只覆盖 5 个高频意图——上传解析、匹配、生成面试题、推进状态、查数据；其余走页面按钮。跑通了再扩。

## 8. 怎么验收"这个对话做对了"

| # | 验收项 | 判据 |
|:--:|---|---|
| 1 | 意图识别准确 | 20 条典型话术（含 5 条模糊），正确路由 ≥ 16 条 |
| 2 | 缺参数能追问 | 说"匹配一下"且上下文无职位时，只追问一次"哪个职位？" |
| 3 | 上下文推断 | 上传后说"适合哪个岗"，能自动用当前职位 |
| 4 | 危险操作必确认 | 淘汰/发布/批量变更 100% 先出确认卡 |
| 5 | 结果卡片化 | 匹配/面试题/数据 三类结果都是卡片不是纯文字 |
| 6 | 权限不越级 | 招聘专员在对话里说"删掉这个用户"→ 拒绝并说明无权 |
| 7 | 成本可观测 | 每轮对话末尾显示本轮耗时与花费 |
| 8 | 降级可用 | 关掉 LLM，页面上所有操作仍可用 |
| 9 | 可回看 | 刷新后会话还在，点开能看历史卡片 |
| 10 | 响应及时 | 读操作首字 < 2s；写操作确认卡立即出现 |

## 9. 5 分钟演示脚本（对话版）

> 评委视角：不点表格，全程"说话"完成一次招聘任务。

1. **开场**（20s）：登录 → 工作台 → 右栏显示当前职位。
2. **上传**（40s）：「我传一批简历」→ 拖 10 份 → 进度条 → 解析结果卡（9 成功 1 失败）。
3. **匹配**（40s）：「看看谁适合后端岗」→ 排名卡 → 展开第 1 名理由（命中/缺失/经验差）。
4. **面试题**（40s）：「给前三个出面试题」→ 三张题卡 → 点开一道看"引用了他的电商项目"。
5. **推进状态**（40s）：「把张伟推到面试」→ 确认卡 → 确认 → 状态更新 + 通知。
6. **数据**（40s）：「这个月哪个渠道效率高」→ 图表卡 + 洞察。
7. **收尾**（20s）：左栏切回"Python 岗筛选"会话，历史都在；右栏点"成本"看本轮花了多少钱。

**总计约 4 分钟**，全程没有进入"表单页"，证明对话式是可用的；再补一句"所有能力在页面上也有按钮，AI 挂了不影响使用"。

## 10. 一句话总结

**TalentMatch = 一个会说话的招聘系统。** 你说需求，Manager Agent 听懂、拆任务、调子 Agent 干活、把结果做成卡片给你；不可逆的事它会先问你一句。它的"智能"不在于会聊天，而在于**背后真的有一整套招聘业务能力被接上了**——这就是它和普通聊天机器人的本质区别。
