# TalentMatch —— AI 驱动的企业智能招聘 Agent 平台：项目设计方案（V1）

> 本文是**从零开发**的完整设计方案。gitee 的 `P1M0U/Resume-Assistant` 仅作参考（借鉴其 RAG 向量检索与多厂商 LLM 路由经验），不以此为底座。

> 参考结构：仿照"同学十五阶段"的**分阶段、逐层递进**风格组织，每阶段目标明确、产出清晰、可验收。

# 第一部分 · 为什么做、做什么

## 1. 产品背景与定位

**一句话定义**：面向企业 HR 团队的 AI 智能招聘 Agent 平台，定位为**"AI 招聘专家"**。

**要解决的核心痛点**：

| 痛点 | 说明 |
|------|------|
| 简历筛选耗时 | HR 每天处理上百份简历，人工看既慢又累 |
| 好候选人被漏掉 | 关键词粗筛容易漏，错失优质候选人 |
| 匹配不靠谱 | 没有科学的评分依据，凭感觉 |
| 招聘流程繁琐 | 通知、安排面试、状态流转全是手动重复劳动 |
| AI 能力不可信 | 单次调用不可解释、不可控成本 |

**产品的价值闭环**（从 PRD 提炼）：

```
企业发布职位(JD)
   │  AI 辅助生成 JD
   ▼
简历批量上传 → AI 解析成结构化数据
   │  (多格式 PDF/Word/图片)
   ▼
智能人岗匹配（技能 / 经验 / 学历加权评分 + 可解释理由）
   │  (Manager Agent 编排)
   ▼
AI 面试辅助（生成个性化面试问题）
   │
   ▼
招聘流程自动化（状态流转 + 通知）
   │
   ▼
数据分析（漏斗 / 周期 / 渠道）+ 成本监控（Token 计量）
   │
   ▼
持续优化招聘策略
```

# 第二部分 · 怎么搭（技术与架构）

## 3. 技术选型

> 原则：**后端沿用 gitee 验证过的 FastAPI + LangChain + SQLAlchemy 路线**，前端用 Vue3，省时间、RAG 好借鉴；不用 PRD 写的 Next.js + PostgreSQL + Celery（对单人从零开发太重）。偏离点在文末 ADR 里说明。

| 层 | 选型 | 理由 |
|----|------|------|
| 后端框架 | FastAPI | 高性能异步、自动 OpenAPI、gitee 已验证 |
| AI 框架 | LangChain + LangGraph | 多 Agent 编排（LangGraph 状态图）、多厂商路由 |
| ORM | SQLAlchemy 2.0 | 稳定、支持多方言 |
| 数据库 | PostgreSQL（可切 SQLite 开发） | JSONB、成熟；开发期 SQLite 免装 |
| 向量库 | ChromaDB | 轻量、本地可跑、gitee 已用 |
| 对象存储 | **MinIO**（S3 兼容） | 简历文件不入库、不放本地盘；本地 Docker 可跑，生产可换 OSS/S3；支持预签名 URL |
| 前端 | Vue3 + TypeScript + Element Plus | gitee 同套、组件全、上手快 |
| 状态管理 | Pinia | Vue3 官方推荐 |
| 鉴权 | bcrypt + JWT | 成熟方案 |
| 任务 | 开发期进程内后台任务，生产可换队列 | 省去装 Redis/Celery 的负担 |
| LLM | 多厂商 OpenAI 兼容（智谱/DeepSeek） | 供应商可切换、避免单点 |

## 4. 总体架构

```
┌──────────────────────────────────────────────┐
│                 前端 Vue3 (Web)              │
│   职位/简历/匹配/面试/流程/看板 多页面        │
└────────────────────┬─────────────────────────┘
                     │ HTTPS / JSON
┌────────────────────▼─────────────────────────┐
│              FastAPI (API 层)                 │
│   routers/v1: auth/job/resume/match/          │
│               interview/application/dash/     │
│               cost/admin                      │
├───────────────────────────────────────────────┤
│         业务服务层 Business Services         │
│   job_service / resume_ingest / matcher /     │
│   pipeline / analytics / cost_tracker         │
├───────────────────────────────────────────────┤
│        🤖 Agent Orchestrator（多 Agent）      │
│   Manager Agent → 调度 5 个子 Agent           │
│   ResumParser│Matcher│Interview│Workflow│Anal │
│         └──── Context Bus（共享上下文）──────┘ │
│         └──── RAG 检索层（向量召回）─────────┘ │
└────────────────────┬─────────────────────────┘
                     │
┌────────────────────▼─────────────────────────┐
│             数据层                            │
│  PostgreSQL(业务) │ ChromaDB(向量) │ MinIO(简历) │
```

**关键点**：AI 能力不散落在各接口里，而是集中在 **Orchestrator**，让 Manager Agent 统一调度，业务层不直接碰 LLM。这是本项目区别于"普通 CRUD + 一个 AI 接口"的核心。

# 第三部分 · 核心能力设计

## 5. 多 Agent 编排架构（PRD §5.2 落地）

> 这是项目最有区分度的部分，也是答辩亮点。

### 5.1 模式选型：为什么选 Supervisor 而不是 Network

多 Agent 协作业界常见五种模式，先对比再定：

| 模式 | 结构 | 典型适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| **Supervisor（监督者）** | 一个中心协调 Agent 拆任务、分派给子 Agent、收结果 | 有明确业务流程、任务可拆分 | 可控、可追踪、易降级、成本可预算 | 协调者是单点，但它只做路由、不存业务状态，挂了可降级为直连各 Agent |
| **Network（网络 / 点对点）** | 子 Agent 平级互相 handoff，谁接谁不定 | 开放式研究、探索型任务 | 灵活、路径多样 | **流程不可预测、难审计、成本不可控** |
| **Hierarchical（层级）** | Supervisor 再管 Supervisor，多层 | 几十个 Agent 的大规模系统 | 可扩展 | 6 个 Agent 用它属过度设计 |
| **Sequential / Pipeline（流水线）** | 固定顺序 A→B→C | 流程确定的批处理 | 简单、快、便宜 | 不灵活，不能按意图组合 |
| **Swarm（蜂群）** | 多 Agent 自由协作、动态交接 | 探索型 | 涌现能力强 | 完全不适合业务系统 |

**结论：本项目用「Supervisor 决策 + 确定性流程执行」的混合方案。**

- **Supervisor 负责"决策"**：理解意图（是"只匹配"还是"匹配+出面试题"），决定跑哪几个子 Agent、按什么顺序。
- **确定性流程负责"执行"**：具体链路（解析→匹配→面试题）的步骤依赖是**写死的状态图**，不允许多 Agent 自由发挥。

**为什么不用 Network（关键理由）**：招聘业务要求 **结果可复现、过程可审计、成本可预算**。Network 模式下 Agent 可随意互相交接，同一个请求两次跑出不同路径——在企业系统里这是事故，答辩时也会被追问"你怎么保证每次结果一致"。

**为什么不纯 Pipeline**：需要上层按意图组合能力。用户点"一键评估"时，系统要知道该串起 MatchEngine + InterviewAssistant 并处理 top3——纯流水线做不到这种弹性。

**为什么不用 Hierarchical**：本系统 6 个子 Agent、一层业务，多层 supervisor 只会增加复杂度而没有收益。

**落地方式**：LangGraph 的 supervisor 模式（中心节点 + 条件路由边）。子 Agent 是图节点，路由由 supervisor 节点决策，边为条件边（conditional edges）；同一图里的固定链路用普通边串起来。

### 5.3 设计原则：先划清 Agent 与 Tool 的边界

**不是所有步骤都该做成 Agent**。LLM 只用在"需要理解/生成"的地方；能用规则算的绝不交给 LLM——这是成本和可复现性的底线。

| 类型 | 判定标准 | 本项目例子 |
|---|---|---|
| **Agent（LLM 参与）** | 输入非结构化、需要理解或生成、允许一定不确定性 | 简历字段抽取、匹配理由、面试题、JD 生成、数据洞察 |
| **Tool / Service（确定性代码）** | 有明确算法、必须可复现、性能敏感 | 技能归一化、规则打分、去重、状态机校验、漏斗统计、token 计费 |

**子 Agent 内部可以调用 Tool**。典型例子是 MatchEngine：先用 Tool 算规则分（确定性、可复现），再让 LLM 基于分数明细写理由（生成）。这样分数稳定、理由自然。

| 项目 | 说明 |
|---|---|
| Agent 能做的事 | 理解、抽取、生成、改写、解释 |
| Agent **绝对不能**做的事 | 算分（要用规则）、判状态合法性（要用状态机）、计费（要用代码）、改库（要经 service） |

### 5.4 六个子 Agent 的职责规格

**总览**：

| # | Agent | 一句话职责 | LLM 形态 | 触发时机 | 阶段 |
|:--:|---|---|---|---|:--:|
| 1 | JDWriterAgent | 职位名+关键词 → 三段 JD | 生成 | 建职位时点「AI 生成」 | 三 |
| 2 | ResumeParserAgent | 简历文本 → 结构化 JSON | 抽取 | 上传/投递完成后 | 四 |
| 3 | MatchEngineAgent | 规则算分 + 排名 + 写理由 | 只写理由 | 点「智能匹配」 | 五 |
| 4 | InterviewAssistantAgent | 生成个性化面试题 | 生成 | 点「生成面试题」 | 六 |
| 5 | WorkflowAutoAgent | 校验状态迁移 + 生成通知措辞 | 润色（可关） | 状态变更时 | 六 |
| 6 | AnalyticsAgent | 统计数字 → 人话洞察 | 文案 | 打开看板 / 生成报告 | 七 |

下面逐个给规格（输入、输出、工具、降级、约束、成本）。

#### ① JDWriterAgent（JD 生成）

| 项 | 规格 |
|---|---|
| **职责** | 输入职位名、部门、关键词，产出结构化 JD：职责 4~6 条、任职要求 4~6 条、技能 8~15 个（已归一） |
| **输入** | `{title, department, keywords[], level?, location?}` |
| **输出** | `{description, requirements, skills[], must_have_skills[], summary}` |
| **工具** | 技能词表归一（Tool）；热门 JD 模板检索（RAG，阶段八后可选） |
| **LLM 用量** | 高（纯生成），用 cheap 模型 |
| **失败降级** | LLM 失败 → 返回按职位名套的通用模板草稿，标记 `ai_generated=false`，让用户手填 |
| **硬约束** | 生成结果**必须可编辑再保存**，绝不直接落库发布；技能必须过词表归一 |
| **成本控制** | 同 `title+keywords` 指纹缓存 24h；目标 ≤15s |

#### ② ResumeParserAgent（简历解析）

| 项 | 规格 |
|---|---|
| **职责** | 把简历纯文本抽成结构化字段 + 每字段置信度 |
| **输入** | `{text, source_format}` |
| **输出** | `{personal, education[], work[], projects[], skills[], certificates[], expected_salary?, field_confidence{}}` |
| **工具** | 无（纯抽取）；抽取后接「技能归一」「日期归一」Tool 做后处理 |
| **LLM 用量** | 高（抽取），用 cheap 模型 |
| **失败降级** | JSON 解析失败 → 修复重试 1 次 → 仍失败返回空结构 + `error_reason`，文件标记 failed，**不阻断同批次其他文件** |
| **硬约束** | 严格 schema；字段缺失填 `null` 不编造；置信度低字段提示人工校对；抽取时**不采性别/年龄/婚育**（避免偏见与合规风险） |
| **成本控制** | 文件 `sha256` 命中直接复用，不重复解析；目标 ≤20s/份 |

#### ③ MatchEngineAgent（人岗匹配）

| 项 | 规格 |
|---|---|
| **职责** | 对「一个职位 × 一批候选人」产出可解释排名与理由 |
| **输入** | `{job_snapshot, candidates_features[]}` |
| **输出** | `{ranked[], each: {score, skill_score, exp_score, edu_score, other_score, matched_skills[], missing_skills[], reason, risks[]}}` |
| **工具** | `rule_scorer`（§8 公式，确定性打分）、`skill_normalizer`、缓存 |
| **LLM 用量** | 中：**只写 reason/risks**，输入是规则算好的明细，不让它打分 |
| **失败降级** | LLM 挂 → 用模板拼理由（"命中 X；缺 Y；经验差 Z 年"），分数照常返回 |
| **硬约束** | 同输入必须同分（可复现）；理由必须引用明细中的技能/年限，**禁止编造** |
| **成本控制** | 理由**只给 top-N 生成**（默认 20），其余只返分数；指纹缓存（职位版本 + 简历 hash）；目标 ≤5s/100 份 |

#### ④ InterviewAssistantAgent（AI 面试辅助）

| 项 | 规格 |
|---|---|
| **职责** | 为一个候选人 + 一个职位生成 6~8 道个性化面试题 |
| **输入** | `{job_snapshot, candidate_resume, match_gaps}`（gaps 直接来自 MatchEngine，不重算） |
| **输出** | `{questions: [{category, question, looking_for, reference, follow_up}]}` |
| **工具** | RAG 检索（相似简历的历史面试题）、技能归一 |
| **LLM 用量** | 高（生成），用 standard 模型 |
| **失败降级** | 失败 → 返回基于缺口的模板问题（"请介绍你在 X 方面的经验"） |
| **硬约束** | **每题必须引用简历中的具体项目/公司，或缺失技能**；禁止"请自我介绍"类通用题；落库后做抽检，不达标算缺陷 |
| **成本控制** | `job+resume` 指纹缓存；同人同职位重复点直接读缓存 |

#### ⑤ WorkflowAutoAgent（流程自动化）

| 项 | 规格 |
|---|---|
| **职责** | 状态变更时：① 校验迁移合法性 ② 生成要发的通知内容 |
| **输入** | `{application_snapshot, from_status, to_status, operator, note}` |
| **输出** | `{allowed: bool, reason?, notification: {channel, subject, body}}` |
| **工具** | `pipeline` 状态机（确定性校验）、通知模板库 |
| **LLM 用量** | **低，默认关闭**：模板能覆盖就不调 LLM，只在下拉列表里的特殊场景开润色 |
| **失败降级** | LLM 挂 → 用模板文案；状态校验与 LLM 无关，永远可用 |
| **硬约束** | **状态合法性绝不由 LLM 判断**——这是状态机 Tool 的职责。Agent 只负责措辞。 |

#### ⑥ AnalyticsAgent（数据分析洞察）

| 项 | 规格 |
|---|---|
| **职责** | 把漏斗/周期/渠道的统计数字，转成 3~5 条人话洞察 + 风险提示 |
| **输入** | `{metrics_snapshot}`（全是已算好的数字） |
| **输出** | `{insights[], risks[], suggestions[]}` |
| **工具** | `analytics` 统计服务（确定性） |
| **LLM 用量** | 低（只写文字），用 cheap 模型 |
| **失败降级** | LLM 挂 → 直出数字 + 模板结论 |
| **硬约束** | 洞察必须**基于给出的数字**，禁止编造趋势；不改变任何统计口径 |

### 5.5 编排机制：Manager 怎么调度

**Manager（Supervisor）的决策五步**：

```
① 接收意图 + 参数（intent, payload）
② 查「意图 → 子任务」映射表
③ 构建 DAG（按依赖排序）
④ 按拓扑序调度；每步失败走降级策略
⑤ 聚合结果 + 轨迹 + 成本，统一返回
```

**意图 → 子任务映射表**（这是 Supervisor 的核心配置）：

| 用户意图 | 触发点 | 调度的子 Agent（按序） |
|---|---|---|
| 生成 / 优化 JD | 建职位页按钮 | JDWriter |
| 上传简历（批量） | 批量上传 | ResumeParser（逐份并行） |
| 智能匹配 | 职位页「匹配」 | MatchEngine |
| 生成面试题 | 候选人页按钮 | （可选先 MatchEngine 取缺口）→ InterviewAssistant |
| 推进状态 | 拖看板卡片 | WorkflowAuto |
| 看板洞察 | 打开分析页 | Analytics |
| **一键评估（组合）** | 职位页「AI 评估 top3」 | MatchEngine → InterviewAssistant × top3 |

**「一键评估」就是 Supervisor 存在的价值证明**：一次点击，串起两个 Agent、服务三个候选人、合并成一份报告。纯接口拼装做不到"按意图自动组合 + 共享上下文 + 统一降级"。

### 5.6 上下文总线（Context Bus）

一次编排内共享状态，**避免下游重算上游**：

```
ContextBus {
  trace_id, intent,
  job_snapshot,        # 职位版本快照（防编排中途被改）
  candidate_ids[],
  resume_features{},   # 解析出的技能/年限 → 给匹配用
  match_results{},     # 匹配明细 → 给面试题用"缺口"
  artifacts{},         # 各 Agent 产出
  usage{}              # 每步 token/耗时/成本
}
```

关键规则：**下游 Agent 不重算上游结果**。面试题直接用匹配算出的 gaps，不再自己解析一遍简历——省一次 LLM 调用，也保证两处结论一致。

### 5.7 失败降级、可观测与成本

**降级三级**：

| 级别 | 情况 | 处理 |
|:--:|---|---|
| 1 | 单 Agent 失败 | 该步用兜底结果（模板/空结构），流程继续，结果标 `degraded` |
| 2 | 单 Agent 超时 | 超时中断（默认 30s），按失败处理 |
| 3 | 依赖缺失 | 前置没成功时跳过依赖它的步骤，明确告知用户"缺哪一步" |

**可观测（轨迹）**：每步写一条 AgentTrace：

```
{trace_id, step_no, agent, input_hash, output_summary, status,
 duration_ms, tokens_in, tokens_out, cost, degraded}
```

前端"编排轨迹"面板据此展示：跑了哪几步、每步耗时、哪步降级。答辩时可直接指着说"这里耗时 2.3 秒、这里降级了所以用模板"。

**成本控制四招**：

| 手段 | 做法 |
|---|---|
| 模型分级 | 解析/抽取用 cheap；面试题/JD 用 standard |
| 缓存 | 文件 hash、职位+简历 hash、同输入 24h |
| 限量 | 匹配理由只给 top-N，不写全库 |
| 预算 | AICall 累计，超阈值告警/拦截 |

### 5.8 三个典型编排场景

**场景 A：批量上传 50 份简历**

```
Supervisor: intent=resume_upload, count=50
  → 建 50 个并行 ResumeParser 子任务（互不依赖）
  → 逐个失败降级，不影响其他份
  → 聚合：成功 47 / 失败 3（附 3 条失败原因）
  → 只用到 1 类 Agent，无需编排复杂链路
```

**场景 B：一键评估某职位 top3**

```
Supervisor: intent=full_eval, job_id=12, top_n=3
  ① MatchEngine 全库评 → 排名 → 取 top3
  ② ContextBus 把每人 match_gaps 传给面试 Agent
  ③ InterviewAssistant × 3 并行生成面试题
  ④ 聚合：排名表 + 每人 8 题 + 轨迹 + 总成本
  → 返回一份「候选人评估报告」
```

**场景 C：面试后推进到 offer**

```
Supervisor: intent=advance_status, app_id=301, to=offer
  ① WorkflowAuto 用状态机校验 interview→offer 合法（确定性命中）
  ② 生成 offer 通知文案（模板优先，LLM 可选润色）
  ③ 写 StageHistory + 触发通知
  → 一步完成，几乎不耗 token
```

| 场景 | 用到的 Agent | 典型耗时 | 典型成本 |
|---|---|:--:|---|
| A 批量解析 50 份 | ResumeParser ×50 | 3~8 分钟 | 中（按份计） |
| B 一键评估 top3 | MatchEngine + InterviewAssistant ×3 | 10~20s | 中 |
| C 推进状态 | WorkflowAuto | <1s | 几乎为 0 |

## 6. RAG 知识增强设计（借鉴 gitee 经验）

**用在哪**：

- 简历解析后，把结构化简历向量化存库，支持"相似候选人检索"（人才库）；
- 匹配时，用 JD 检索相似历史简历，辅助匹配理由；
- 面试题生成时，检索类似简历的历史面试题/面试记录，让问题更贴合。

**流程**：

```
文档 → 切片(text_splitter) → 向量化(embedding) → 存 ChromaDB
查询 → 向量化(query) → 检索 top-k → 拼进 prompt → LLM 生成
```

**借鉴 gitee（写进设计、实现时参照）**：
- 切片策略（避免把简历切碎导致语义断裂）；
- Chroma 的集合划分（resume_collection / job_collection 分开）；
- 向量化失败降级（VECTOR_STORE_ENABLED 开关，关了也不影响主流程）。

**关键设计决策**：向量库只放"可检索的语义片段"，不替代关系库的主数据结构——简历原文和结构化字段仍存 PostgreSQL，向量只用于相似检索。

## 7. 数据模型（核心实体）

> 详细字段见后续数据字典，这里先给核心实体关系。

```
User(用户) 1─* Job(职位) 1─* Application(应聘)
User 1─* Candidate(候选人)
Candidate 1─* ResumeFile(文件) ─ 1─ Resume(解析结果)
Job + Candidate → MatchResult(匹配结果)
Application → StageHistory(状态流转历史)
User/Job → AICall(AI 调用记账)
```

7 大核心表 + 2 辅助表（User / LLMConfig 沿用基础）：

| 表 | 关键字段 | 说明 |
|----|----------|------|
| User | role(recruiter/manager/admin) | 三角色 |
| Job | title, skills, must_have_skills, status | 职位 + 必备技能 |
| Candidate | dedupe_key(去重), skills, years_experience | 候选人档案 |
| ResumeFile | sha256(防重复解析), status | 上传的原始文件 |
| Resume | structured(JSON), confidence | 解析出的结构化字段 |
| Application | job_id, candidate_id, status, source | 应聘记录 |
| StageHistory | from_status, to_status | 状态流转留痕 |
| MatchResult | score, matched/missing_skills, detail | 可解释匹配结果 |
| AICall | feature, tokens, cost | AI 成本记账 |

**三个必须讲清的设计点**：
1. **去重**：`candidate.dedupe_key` = 邮箱/手机号归一，同人多份简历合并成一条，不能只看姓名。
2. **可解释匹配**：`MatchResult` 存四维分 + 命中/缺失技能 + 完整理由明细，不是只存一个 0.83 的数字。
3. **成本可观测**：每次 LLM 调用写 `AICall`，按职位/功能聚合，超预算能拦。

## 8. 匹配算法（规则打分 + LLM 写理由）

> PRD 没给算法，这里设计成"可解释、可评测"的规则分 + LLM 只做润色：

```
score = 100 * (0.50×技能 + 0.30×经验 + 0.12×学历 + 0.08×其他)

技能分 = 0.7×必备技能覆盖率 + 0.3×加分技能覆盖率（命中必备 <100% 时整体 ×0.6 惩罚）
经验分 = 年限达标(0~0.6) + 相关领域(0~0.3) + 稳定性(0~0.1)
学历分 = 满足1.0 / 超配0.9 / 不足0.5
其他   = 地点0.5 + 薪资重叠0.3 + 行业0.2
```

- **打分用规则**（稳定、便宜、可解释）；**LLM 只生成理由**（把它讲成一句话），理由基于匹配明细，不让他瞎编。
- **权重可配**，用标注集评测调参，不是拍脑袋。
- **缓存**：指纹 = 职位版本 + 简历内容 hash，重复匹配直接复用，不重复计 LLM 费用。

## 9. 核心流程（端到端）

```
HR 建职位（可 AI 生成 JD）
  → 提审批 → 用人经理审批 → 发布
  → 候选人传简历（或 HR 批量上传）
  → ResumeParser 解析成结构化 + 校对
  → 点"智能匹配" → MatchEngine 全库评分排名（可解释）
  → 选候选人 → InterviewAssistant 生成面试题
  → 推进状态 new→screening→interview→offer→hired（或 rejected）
  → 状态变更触发通知
  → 看板实时看漏斗 / 周期 / 渠道
```

**做什么**：

## 阶段四：简历上传与解析

**做什么**：
1. **多文件上传到 MinIO**：校验类型/大小 → 算 sha256 命中即复用 → 未命中存对象并写 `resume_file`（`bucket`/`object_key`/`etag`）；下载走 10 分钟预签名 URL。
2. 多格式解析链：PDF(→降级 PyMuPDF) / DOCX / 图片(可走视觉)。
3. 大模型把简历文本抽取成结构化 JSON（姓名/联系方式/教育/经历/技能）。
4. LLM JSON 容错（包 Markdown 围栏、缺字段、重试、字段级兜底）。
5. 去重：同人多份合并成一个候选人。
6. 前端上传页 + 解析结果校对页（低置信度字段标黄可改）。

**产出**：上传（MinIO）→ 解析 → 结构化 → 校对 → 去重全链路。

**验收**：传 4 份（PDF/DOCX/图片混合）出结构化；同一人两份只留一条；同文件重复上传不重复解析；乱码文件不报 500 提示手动录入；下载简历用的是预签名 URL 且写审计。

**借鉴 gitee**：文件解析器结构、LLM JSON 提取的容错思路、解析失败降级。

## 阶段五：智能人岗匹配

**做什么**：

**产出**：可解释的匹配引擎 + 排名 + 评测报告。

## 阶段九：多 Agent 编排

**借鉴 gitee**：多 Agent 的组织方式与状态管理可参考其 agentics 目录分层；但**编排层（LangGraph Supervisor）需自己设计**，gitee 没有这块。

## 10. 非功能与合规
